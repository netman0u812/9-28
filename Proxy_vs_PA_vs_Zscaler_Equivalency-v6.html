Web Proxy vs. Palo Alto vs. Zscaler

Three-Platform Enforcement Equivalency Analysis — DLP, Malware, File Blocking, URL Filtering, TLS Integrity • Generated 2026-07-16
Scope and sources

This report extends the existing PA vs. Zscaler — DLP & Malware/Threat Prevention Equivalency Analysis (v8.1) to a third platform: the Skyhigh Secure Web Gateway (formerly McAfee Web Gateway) forward proxy, analyzed from a Coordinator configuration backup dated 2026-06-03 (appliance version 12.2.23).

  • Proxy data — parsed directly from the backup's exported policy library: 3 custom rule-group files (144 rules), 41 DLP dictionaries, 9 DLP category rulesets, 57 block-action templates, 8 redirect actions, 7 auth methods, 2 antivirus engines, 4 URL-categorization (TrustedSource) engine instances, 4 ICAP integrations, and 223 lists.
  • PA data — as documented in PA Panorama Security Policy Documentation v8 (45 rules, cross-verified against live Panorama config, two clusters: LV/AZ/RI and MID/WIN).
  • Zscaler data — as documented in the v8.1 equivalency report (direct API export: 22 DLP rules / 33 engines / 166 dictionaries, plus Malware and Advanced Threats policy).

Critical caveat carried over from the proxy analysis: the backup only exports the appliance's custom rule-group library. The built-in/default rule sets — which is where URL-category blocking and DLP-engine wiring normally live on this platform — are not present in this backup. Every proxy finding below distinguishes between "configured as an object" (exists in the backup) and "confirmed enforced" (wired to an active, enabled rule) — the same discipline the PA and Zscaler reports already apply. Enforcement status is determined by checking effective enablement up the full rule-group hierarchy, not just each rule's own flag, since a rule can read enabled="true" while sitting inside a disabled parent group.

SaaS Tenant Restriction (Azure AD) — Deep Dive

Confirmed active on the proxy; not confirmed either way on PA or Zscaler

The proxy runs Microsoft's Tenant Restrictions v1 mechanism inside an Azure AD Tenant Restrictions rule group: it strips any client-supplied Restrict-Access-To-Tenants / Restrict-Access-Context headers (preventing spoofing), then writes its own values — sourced from two live-updating subscribed lists (Prod_TenantR_Portals, Prod_TenantR: Domains) — on every request to Microsoft's sign-in domains. This blocks employees from authenticating into personal Microsoft accounts or unauthorized organizations' M365 tenants from the corporate network. All 6 rules in this group are confirmed active.

Microsoft's current recommendation is actually Tenant Restrictions v2, which moves enforcement into Entra cross-tenant access policies rather than depending on proxy/firewall header injection — worth considering as the target state rather than replicating v1 on a second platform.

URL / Content Filtering — Deep Dive

Confirmed active

The proxy's URL Filter rule group contains a confirmed-active, global 47-category blocklist (Category Blocklist) plus a separate rule blocking cloud-storage categories specifically.

One real limitation remains: the 47 category IDs (e.g. com.scur.category.202) can't be resolved to human-readable names — the vendor's internal ID-to-name taxonomy isn't included in this backup, so a category-by-category comparison against PA's named list (adult, gambling, malware, etc.) isn't possible without that mapping. Count-wise, 47 meets or exceeds PA's ~30–34.

By contrast:

Cluster B is materially weaker (only 1 of 7 profile groups blocks anything, and just 12 categories).

What This Means for the Traffic-Class Framework

Three platforms, three different enforcement shapes — not a simple maturity ranking

No single platform is "ahead" across the board:

  • Zscaler is the most mature on DLP and malware/threat blocking — the only platform confirmed actively enforcing (not just alerting) in both domains, consistent with 3+ years of tuning.
  • Palo Alto is the strongest on file blocking and the only one with confirmed comprehensive URL category enforcement — but its DLP and most of its threat-prevention stack are alert-only, a known gap against PA's own published best-practice guidance.
  • The proxy has the richest DLP content definitions of the three (genuinely CVS/Aetna-specific: HICN, GEMS ID, Member ID) and a mature TLS-integrity layer none of the other reports examine — but its DLP wiring is unverifiable, its AV stack lacks a working second layer, and its URL-category policy isn't visible in this export at all.

For the enforcement strategy: the proxy is very likely carrying a real, active role in the traffic-class model for legacy/decrypted web egress — but this backup can't confirm which of its defined controls (DLP especially) are actually in the live enforcement path versus configured-and-dormant. Pulling the appliance's default/built-in rule set (not just the custom library) would close that gap and let this become a like-for-like comparison rather than a partial one.

Recommendations — Path to Parity

Framing

The findings above describe where each platform's configuration stands today, not a scorecard of which vendor is "better." PA is 6–8 months into a rollout Zscaler has had 3+ years to mature, and PA's own documentation already names its next steps. The items below are concrete, additive fixes aimed at closing specific gaps — not a case against the platform.

1. Add HICN detection to NAB - Initial Data Filtering — Ready to implement

PA's DLP profile uses only Palo Alto's predefined generic pattern library (SSN, credit card, bank routing, AWS/RSA keys, national IDs) — it has no pattern for Medicare Health Insurance Claim Numbers, even though this is one of the proxy's best-covered categories and a CMS-regulated identifier for a healthcare payer. This is a straightforward gap to close, not a redesign: the proxy's existing HICN dictionaries translate directly into two PA Custom Data Patterns.

New Data PatternTypePatternSource
HICN – Numeric Format Regular Expression \b\d{3}-?\d{2}-?\d{4}-?[A-Za-z]{1,2}\b Consolidated from the proxy's CVS Health HICN and HICN RegEx dictionaries — legacy SSN-shaped HICN with 1–2 letter Medicare/RRB suffix code.
HICN – Keyword/Context Regular Expression (?i)\b(HICN|HIC\s*#|HICN\s*#|HIC\s*No\.?|HICN\s*No\.?|Medicare\s+HIC(?:N)?|Health\s+Insurance\s+Claim\s+Number)\b Deduplicated from the proxy's 14-term HICN Terms / CVS Health HICN Keywords dictionaries.

Implementation path: add both as new objects under Objects → Custom Objects → Data Patterns in the device group that owns NAB - Initial Data Filtering (shared across Meritain, PPOM, LV-Colo, and the Proxy SPGs), then attach them to that profile the same way the existing 22 predefined patterns are attached.

Decision needed, not assumed: the profile's current rule is alert-only for all 22 existing patterns (PA's unmodified default, not a deliberate CVS choice). Adding HICN to that same rule inherits alert-only behavior. If HICN should actually block — which would make it the one pattern in this profile enforcing rather than just logging — it needs its own rule with action=block, since editing the shared rule's action would change behavior for all 22 existing patterns at once.

2. Port TLS/certificate-integrity checks to PA's Decryption Profile — Mostly ready, two partial mappings

The proxy runs 8 distinct certificate-validation checks on decrypted HTTPS traffic (10 rules across two rule sets, same logic in each). PA has a direct architectural equivalent — the Decryption Profile attached to SSL Forward Proxy decryption policy — and most of these checks are native toggles there, not new capability. This is a genuine like-for-like port, not a proxy-specific concept being forced onto PA.

Proxy Rule (enabled)PA Decryption Profile EquivalentMapping
Block Expired Server / CA CertificatesSSL Forward Proxy → Block sessions with expired certificatesDirect match
Block Self Signed CertificatesSSL Forward Proxy → Block sessions with untrusted issuersDirect match — a self-signed cert is untrusted by definition once it's not in the trust store
Block Unknown / Untrusted Certificate AuthoritiesSSL Forward Proxy → Block sessions with untrusted issuersDirect match — PA doesn't distinguish "unknown CA" from "untrusted CA" the way the proxy does; both collapse to one toggle
Block Revoked CertificatesCertificate Profile (attached to decryption) → OCSP/CRL checking enabled, Block session if certificate status is unknownDirect match, but lives on the Certificate Profile, not the Decryption Profile itself — needs both objects checked together
Block Weak Key ExchangeSSL Protocol Settings tab → minimum TLS version + allowed key exchange algorithmsPartial — PA restricts by protocol version/cipher suite, not a standalone "key exchange bits" threshold like the proxy's. Achievable by disabling weak suites, not a single equivalent toggle.
Block Unsafe Signature AlgorithmsNo direct equivalent foundGap — PAN-OS Decryption Profiles don't expose a signature-algorithm blocklist. Would need Certificate Profile minimum key-size settings as a partial substitute, or confirmation this is enforced elsewhere.
Block Common Name MismatchNo direct equivalent foundGap — this is a proxy-specific check (requested hostname vs. presented cert CN/SAN). PA's forward-proxy re-signing model doesn't expose an equivalent standalone toggle in the Decryption Profile.
Block Certificate Chains with Violations (path length)No direct equivalent foundGap — not a standard Decryption Profile toggle; would need verification against your specific PAN-OS version.
5 of 8 checks port cleanly with no new capability required — just configuration. The remaining 3 (signature algorithm, CN mismatch, path length) are genuine gaps worth a direct conversation with your PA engineering contact or Palo Alto TAM before assuming they're unaddressable, rather than being logged here as confirmed-impossible.

3. Port CONNECT port restriction (SSH/Telnet tunneling) to PA — Ready to implement

The proxy blocks HTTPS CONNECT tunnels to destination ports 22 (SSH) and 23 (Telnet) — a defense against tunneling raw protocols through the HTTPS port to evade inspection. PA is App-ID native, so the equivalent is stronger than a straight port copy: a Security Policy rule denying the ssh and telnet applications outright (App-ID identifies these regardless of which port they run on, closing the exact evasion case the proxy's rule exists to catch), plus the same explicit tcp/22 and tcp/23 service-based deny as defense-in-depth matching the proxy's behavior exactly.

This would sit well as a Security Policy rule in the pre-rulebase, ahead of the general internet-egress allow rules, in whichever device group(s) carry the proxy's CONNECT-tunneled traffic today.

4. Not portable / no action needed

  • Geolocation blocking — the proxy's Geolocation.Blocked.Countries list is currently empty (0 entries) on the source system. There's nothing configured to port; if a country blocklist is wanted on PA, it would be a new policy decision, not a migration of existing proxy policy.
  • Proxy-chaining prevention (blocking 31 known internal proxy hostnames) — this defends against a proxy-architecture-specific failure mode (traffic looping back through another Aetna proxy) that doesn't have a meaningful PA equivalent; not recommended for porting.

5. Further parity items identified above, not yet scoped into fixes

Flagged here for tracking; each would need its own scoping pass before an implementation plan like the HICN fix above:

  • DLP action posture — PA's own Enterprise DLP documentation already recommends moving from Alert to Block once false-positive rates are understood; this affects the other 22 patterns in NAB - Initial Data Filtering, not just the new HICN additions.
  • Threat Prevention posture — Vulnerability Protection's "Best Practice" profile has zero deliberate blocking rules despite the name; Palo Alto's own guidance recommends transitioning from Alert-All to the predefined strict/blocking profiles.
  • Cluster B (MID/WIN) parity — no DLP profile exists in this cluster at all; bringing it to Cluster A's baseline (even alert-only) would close the widest gap identified in this report.
