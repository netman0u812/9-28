How Palo Alto Processes Traffic

Every packet is evaluated in the same general pipeline, regardless of device group. This section is general Palo Alto Networks architecture, provided as context for the environment-specific detail that follows.

1. Zone determination

The firewall determines the packet's source zone from the ingress interface, and its destination zone via a forwarding lookup. Security policy is matched on zone pairs, not directly on interfaces \u2014 this is what the Zone Flow Model below documents for each device group in this environment.

2. Security policy: pre-rulebase, local, post-rulebase, default

In a Panorama-managed device group, rules are evaluated in a fixed order: pre-rulebase rules (pushed from Panorama, evaluated first) → any local rules configured directly on the firewall itself → post-rulebase rules (pushed from Panorama, evaluated last, typically catch-all/cleanup policy) → the built-in default intrazone-allow / interzone-deny rule if nothing else matched. Rules are evaluated top-down within each stage; the first match wins.

Confirmed in this environment: all 45 rules documented in this file are pre-rulebase. Both DG_LV_Egress and DG_LV_EXT_DMZ also carry a Default_Deny_APP post-rulebase rule (any zone → Untrust, deny) \u2014 a real, concrete example of the post-rulebase catch-all pattern, confirmed directly in the live configuration rather than assumed from general PAN-OS documentation.

3. Action: allow or deny/drop

If no rule matches, the built-in default rule applies (allow within a zone, deny between zones). A deny/drop match ends processing immediately \u2014 the session never reaches content inspection. Only allowed traffic proceeds to the next stage.

4. Content-ID \u2014 Threat, DLP, and application content inspection

For allowed traffic, the Security Profile Group attached to the matching rule determines which content inspection engines run: App-ID (confirms the actual application, which may differ from what the initial ports suggested), Threat Prevention (antivirus, anti-spyware, vulnerability protection signatures), Data Filtering (DLP pattern matching \u2014 see the Data Filtering Profile section below for this environment's actual configured patterns), and URL Filtering / WildFire / File Blocking. Any of these can still block or reset a connection after the security rule has already allowed it \u2014 a rule's Allow action is necessary but not sufficient for traffic to actually reach its destination unmodified.

5. Egress

Allowed, inspected traffic is forwarded out the interface bound to the destination zone.

Logging Coverage — Finding

Not every rule reaches the same logging destination.

35 of the 43 rules confirmed against live config forward to ForwardtoPanoramaCollector — a profile that sends every log type (traffic, threat, wildfire, URL, data, tunnel, auth, decryption) to Panorama with no filtering (filter "All Logs" on each log type, send-to-panorama yes).

The remaining 8 rules use a log-forwarding profile literally named default, which does not exist as a defined object anywhere in this configuration file. Absent a defined profile, these rules most likely rely on local logging on the firewall itself rather than reaching Panorama — this should be confirmed directly against the device, since it wasn't independently verified beyond the absence of a default profile definition in this config export.

All 8 are in DG_LV_Egress, and they're not random: the entire PPOM cluster, the LV-COLO cluster, and two Meritain rules — including LAN-MERITAIN-WG-NO-INTERNET-ACCESS, a Drop rule, meaning even blocked-traffic events for that segment may not be reaching central logging.

Data Filtering Profile — Processing Rules

This profile alerts on matches; it does not block them.

Confirmed in the live configuration: rule1's action is alert across all 22 patterns — there is no block rule in this profile. Traffic containing a matched pattern (SSN, credit card number, AWS keys, etc.) is logged but is not prevented from leaving.

Worth noting: Alert is Palo Alto's own default action for DLP rules — per PA's documentation, "the default action is Alert," and Block must be explicitly configured. So this may not reflect a deliberate CVS decision to alert-only; it may simply mean the default was never overridden. Either way, whether this should be tightened to a blocking action is a policy decision outside the scope of this document — flagged here because the practical effect (sensitive data isn't stopped, only logged) is significant regardless of whether it was a deliberate choice or an unchanged default.
